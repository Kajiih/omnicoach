# Omni Toolkit Roadmap

This document serves as the single source of truth for architectural milestones, performance investigations, and planned ecosystem integrations for Omni.

Items here represent design areas and technical directions to evaluate rather than fixed implementation mandates.

## Prioritized Next Steps

1. **Consolidate `CodeLintProject` & `CodeLintGraph` (§1, *Project-Wide Abstraction & Interface Design*)**: Unify `ProjectIndex` and `ProjectFacts` (plus the duplicate graph edge indices in `render.rs` and `query.rs`) over one `FileSource`, move formatted presentation strings out of `CodeLintProject` into rule files, and deduplicate `.omnicoach.toml` `[architecture]` loading.
2. **Agent & Parallel `jj` Workspace Safety Rules (§1, *Candidate Rules & Rule Follow-ups*)**: Add `unbounded-jj-log`, `subcommand-before-global-flags`, multi-workspace `jj` rewrite safety checks, and shell/command-shape guardrails (`command_lint` + `hook`).
3. **Rust Hook Cold-Start & CST Walk Attribution (§2)**: Evaluate ancestor-only or lexer-level Rust header probing for `omnicoach hook` on macro-declared crates (`~30 ms`) alongside single-pass Rowan CST extraction.
4. **Contributor Documentation & Browser Playground (§4, §5)**: Document `ProjectCodeRule` and `ProjectExample` in [docs/dev/adding_a_rule.md](docs/dev/adding_a_rule.md) and evaluate multi-file virtual project inputs and `command`/`graph` preview in `omnicoach-playground`.

## 1. Architecture, Rule Engine & Candidate Rules

### Architecture & Conformance

Design: [ADR 006](docs/dev/decisions/006_architectural_dag_and_conformance.md). Enforcement: `src/architecture.rs` (crate graph definition), `src/code_lint/project/architecture.rs` + the 8 `Topic::ARCHITECTURE` rules (native conformance engine), and `tests/architecture_conformance.rs` (self-dogfooding & seeded-breach test suite).

- **Conformance CST Edge Cases (Watch List)**:
  - *Current*: `summarize_rust_file` skips `#[cfg(test)]` items, attribute token trees (such as `#[case(...)]`), and `macro_definition` bodies (production macros `architecture_component!` and `rule_test!` expand either to a doc attribute or inside `#[cfg(test)]`), and assumes paths do not start with a root-anchored leading `::` (`::omnicoach::...` or `::brush_parser::...`).
  - *Target*: If production `macro_rules!` macros calling cross-component helpers (`$crate::...`) are introduced outside `src/lib.rs`, if root-anchored `::` paths appear, or if inline `#[cfg(test)]` modules need DAG enforcement (with a `TestUtils` allowance for rule tests and inline `mod` `super::` unwinding), extend `summarize_rust_file` accordingly.
- **Non-transitive DAG edges**: every edge is transitive today, so a component reaches everything its dependencies reach. A "private" edge (a dependency that dependents do not inherit) would let the graph express isolation rules that currently need bespoke conformance checks.
- **Compiler-enforced subtree visibility (`pub(in crate::...)` / `pub(super)`)**: `code_lint::{ast,semantic,policy,contract,suppression,graph}` and `command_lint::{vcs,command,contract}` now use `pub(in crate::code_lint)`, `pub(crate)`, or `pub(super)`; tighten individual rule submodules under `code_lint::rules` and `command_lint::rules` once `rule_test!` and external benchmarks no longer require `pub mod` rule paths.
- **Intra-component layering of `code_lint::ast::{python,rust}` (investigate)**:
  - *Current*: the language modules form one component (`CodeLintAst`), so conformance checks neither that `python.rs` / `rust.rs` only route (`mod` + `pub use`) nor that their submodules form a DAG. The internal layering (syntax primitives → definition models → fact extractors) is a convention, and `classes` ↔ `functions` was a cycle nothing reported.
  - *Target*: evaluate extending `src/code_lint/project/architecture.rs` (pure-router check, intra-component submodule DAG) to these subtrees, or modeling the layers as sub-components in `src/architecture.rs`.
- **Overlapping Python class attribute walks (`ast::python::{classes, bindings, declaration_order}`)**:
  - *Current*: `PythonClassInfo` in `src/code_lint/ast/python/classes.rs` has three separate attribute-extraction methods (`attribute_definitions`, `annotated_attributes`, `instance_attribute_annotations`), `src/code_lint/ast/python/bindings.rs` has a fourth (`extract_instance_attribute_declarations`), and `src/code_lint/ast/python/declaration_order.rs` has a fifth (`python_public_attributes` for class signature summaries). Each serves slightly different scope rules today (`attribute_definitions` walks `__init__` + post-init methods and deduplicates first definitions; `annotated_attributes` walks class body + `__init__` annotations and checks class-wide in-place mutations; `instance_attribute_annotations` walks all instance methods for inline `self.x: T` annotations; `extract_instance_attribute_declarations` walks `__init__` `self.x = ...` excluding class-body names; `python_public_attributes` walks public class-body `AnnAssign`s and `__init__`/`__new__` `self.<attr>`/`cls.<attr>` assignments).
  - *Target*: Revisit and investigate unifying or sharing the underlying class-attribute traversal if another attribute rule or consumer is added.
- **Intra-component module-level cycle detection (optional reporting)**:
  - *Context*: `define_architecture!` enforces acyclicity between components, while file-to-file (`Module ↔ Module`) mutual dependencies inside a single component (e.g. `rule_declaration.rs ↔ rule_declaration/options.rs` or `ripgrep/crates/ignore` `walk ↔ dir`) are currently invisible to `CodeLintProject`. Although a component is agnostic of its internal implementation split, surfacing intra-component module SCCs (or enforcing intra-component module DAGs where desired; see also the `code_lint::ast::{python,rust}` item above) is a natural extension of `summarize_rust_file` / `ImportMap`.
- **Standalone Rust crate extraction (`omni-architecture`, `omni-graph`, `tagonomy`)**:
  - *Roadmap*: See [docs/dev/crate_split_roadmap.md](docs/dev/crate_split_roadmap.md) for the full crate boundary analysis, pre-split architectural seams (`Source` vs. `Diagnostic` and unified Rust module/reference path resolution), and per-crate scope.
  - *Context & Ecosystem*: A crates.io survey (`cargo_pup`, `archaven`, `zoning`, `archunit`, `rust_arkitect`, `cargo-modules`) shows no published crate combines in-file compiler-checked component declarations (`architecture_component!`), compile-time acyclicity by declaration order (`define_architecture!`), subtree inheritance, sibling isolation, single canonical paths, and external-crate encapsulation (`zoning` is conceptually closest with ordered zones and module seals; `cargo_pup` runs inside nightly `rustc` over a `pup.ron` rule list). External download volume for Rust architecture crates is tiny (`cargo_pup` ~5k, `archaven` ~860), so extraction is driven by reuse across our own Rust repositories rather than broad adoption.
  - *Target*: Once the DAG design items above settle and a second Rust repository needs it, extract the zero-dependency `define_architecture!` / `architecture_component!` macros (`[dependencies]`) and the `ra_ap_syntax`-backed CST conformance runner (`[dev-dependencies]` behind a `check` feature) into a workspace/standalone crate.
- **Multi-Language Architectural Conformance in `.omnicoach.toml` (Python & Rust) — Follow-ups**:
  - *Principle (Per-Language Isolation)*: Abstractions, components, and module graphs never span languages. Each language in a repository defines its own self-contained component DAG, and any cross-language call (such as Python importing a compiled PyO3 extension, FFI, or IPC) crosses a hard boundary that is modeled as an external dependency (`owns-external`), never as a shared cross-language component.
  - *Current*: Implemented in `src/code_lint/project/architecture.rs` and exposed as 8 native `Topic::ARCHITECTURE` rules (`undeclared-component-dependency`, `sibling-module-dependency`, `cross-component-relative-path`, `unowned-external-dependency`, `private-component-import`, `reexported-public-item`, `unmapped-architecture-module`, `invalid-architecture-component`; design in [03_design.md](docs/dev/project_linting/03_design.md)). Supports both `.omnicoach.toml` `[architecture]` declarations (for Python and Rust) and in-file Rust `define_architecture!` (in `src/architecture.rs` or `src/architecture/mod.rs`) / `architecture_component!` macros.
  - *Open follow-ups*:
    - **Typed Python `architecture` module & mixed-root polyglot isolation**: Compare a typed Python `architecture.py` / `architecture/__init__.py` declaration (giving static type checkers typo-proof component references, IDE rename/navigation, and exhaustiveness, mirroring Rust's `src/architecture.rs`) against `# omni:component = "..."` comment headers, and ensure per-language architecture specifications stay independent when a single root directory hosts both `pyproject.toml` and `Cargo.toml` (today `.omnicoach.toml` has one untagged `[architecture]` table, so a root `[architecture]` written for Python also evaluates `src/*.rs` and conflicts with `src/architecture.rs` unless the languages live in subdirectories).
    - **Unused `public-exports` / dead cross-module export detection**: Flag entries in `public-exports = [...]` that no external component imports across the project.
    - **Framework-specific string dependency plugins**: Support framework-specific string dependency references (such as Django `ForeignKey("app.Model")`) when a downstream Python repository requires them.
    - **Per-caller interface visibility & distributed `tach.domain.toml` files**: Evaluate per-caller `public-exports` visibility or distributed domain config files if a multi-team repository outgrows a single root `.omnicoach.toml`.
    - **Cross-process / on-disk summary cache**: `ProjectIndex` currently caches `Arc<PythonFileSummary>` and `Arc<RustFileSummary>` in memory per process (hybrid CLI pre-seed + lazy on-demand hook resolution). Revisit a persistence cache only if cold CLI latency on a >10,000-file repository exceeds `1 s`.
    - **Workspace-wide performance attribution across Rust vs. Python & external crates**: See §2 ("Workspace-Wide Rule Performance: Rust vs. Python & External Crate Attribution").
- **Project-Wide Abstraction & Interface Design (`CodeLintProject` & `ProjectContext` — Investigate)**:
  - *Context & Problem*: Foundational path normalization (`config::lexical_normalize`), source-root discovery (`ProjectLayout`), module-path derivation (`rust_module_from_relative`, `python_module_of_path`), relative Python import resolution (`resolve_relative_python_package`, `resolve_relative_python_module`), and `.omnicoach.toml` / `define_architecture!` component resolution (`ArchitectureSpec::resolve_component_of_module`) are now shared across `CodeLintProject` (`ProjectIndex`, `ProjectFacts`, `layout.rs`, `architecture.rs`, and `hook/runner.rs`). However, the codebase still maintains two higher-level project fact structures (`ProjectFacts` in `CodeLintGraph` built for `omnicoach graph` and `ProjectIndex` / `ProjectContext` in `CodeLintProject` built for `ProjectCodeRule`), and `CodeLintGraph` maintains two adjacency/edge indices (`GraphEdgeIndex` in `render.rs` and `IndexedProjectGraph` in `query.rs`). In addition, while the execution plumbing (`ProjectCodeRule`, `FileSource`, `ProjectLayout`, `ProjectIndex` slot memoization, and multi-file `rule_test!`) is rule-agnostic, the extracted summaries (`PythonFileSummary`, `RustFileSummary`) and `ProjectContext` query methods were shaped around the first three consumer families (`uninherited-protocol`, C3 MRO docstring inheritance, and `Topic::ARCHITECTURE`), and `ProjectCodeRule` only models per-file forward queries (`check(rule, path, file, project, options)`).
  - *Immediate cleanups*:
    - **Move diagnostic presentation formatting out of `CodeLintProject` into `CodeLintRules`** ([ADR 012](docs/dev/decisions/012_module_placement_by_abstraction.md)): return structured owner prefixes (`Vec<String>`) on `UnownedExternalDependencyFinding` instead of a pre-formatted backtick string, and `Option<String>` on `PrivateComponentImportFinding` instead of `EXPORTED_ITEM_PLACEHOLDER`, so rule files own message formatting.
    - **Single-source `.omnicoach.toml` `[architecture]` loading**: remove the fallback `PartialConfigWithArchitecture` TOML parser in `src/code_lint/project/index.rs` once direct `ProjectIndex::new` callers pass `Config::architecture` (sharing one loader in `src/config.rs`).
    - **Eliminate `MemoryFileSource` copying in `omnicoach graph`**: `collect_project_facts_with_config` in `src/code_lint/graph/facts.rs` currently materializes an in-memory `MemoryFileSource` over already-read files to query `ProjectIndex`; pass a shared `FileSource` / `ProjectIndex` directly as `ProjectFacts` and `ProjectIndex` converge.
    - **Explicit working-directory root for long-lived embeddings (`CACHED_CURRENT_DIR`)**: `src/config.rs` caches `std::env::current_dir()` once per process (`LazyLock`), which is valid for single-shot CLI and hook invocations (including `crates/omnicoach-py`'s CLI entrypoint); any long-lived in-process embedding (such as a public `import omnicoach` Python SDK or LSP server; see §4) must pass explicit root paths instead of relying on process working directory.
  - *Investigation & Design Questions*:
    - What is the right fundamental abstraction for project-wide facts in `CodeLintProject` so `omnicoach code`, `omnicoach hook`, and `omnicoach graph` share one coherent module, symbol, and dependency model instead of parallel `ProjectFacts` and `ProjectIndex` pipelines (and so `CodeLintGraph` shares a single edge/lookup index across `render.rs` and `query.rs`)?
    - Which facts belong in a general, language-agnostic module summary versus language-specific or demand-computed queries (`PythonClassSummary` currently stores rule-specific method buckets `public_non_property_methods` and `documented_methods`, and `RustFileSummary` only extracts module/architecture headers rather than general `pub struct` / `pub trait` / `pub fn` symbol exports), and how do SOTA multi-file analyzers (Ruff `ty`, `rust-analyzer`, `oxlint`) layer body-free module interfaces against on-demand symbol resolution without paying for unused fields?
    - How should the rule contract represent rules that require whole-workspace aggregation or reverse call/import indexes (`unused-public-export`, `single-caller-public-api`, `duplicate-abstraction-signature`) while preserving fast single-file `omnicoach hook` execution?

### Rule Engine & Declarative Rules

- **Unified Single-Pass AST Visitor Dispatch**:
  - *Context & Problem*: Today, each registered rule implements `check_file` independently and executes its own AST search or traversal over the file (with common facts shared via `OnceLock` on `ParsedFile`). While Python AST walks over contiguous `ruff_python_ast` slices are cheap, independent walks scale linearly as $O(\text{files} \times \text{rules})$ as the rule registry grows past the current 76 code rules (and on Rust, each walk materializes Rowan red-tree cursors; see §2).
  - *Investigation & Design Questions*:
    - Investigate how high-throughput linters dispatch rules. (e.g. Ruff's `Checker` uses a single AST walk with match arms and $O(1)$ bitset checks; Biome groups subscriptions by `SyntaxKind`; Clippy fuses passes into combined callbacks).
    - Can we establish a rule interest declaration (e.g. target node kinds) early in the trait lifecycle without breaking existing rule independence?
    - How do we handle rules that need multi-stage context (like `environment_variable_in_function` traversing upward or `too_many_assertions` counting inner blocks) within a unified traversal?
  - *Trigger*: When per-rule AST walk overhead becomes a measured bottleneck relative to parse and shared-extractor time (see §2).
- **Rule Naming Canonicalization (`heck`)**:
  - *Target*: Support case-insensitive and format-tolerant rule selection (matching `SingleLetterName`, `single-letter-name`, and `single_letter_name` interchangeably).
  - *Trigger*: When adding declarative AST rule files or multi-rule alias configurations.
- **User-defined project rules (investigate)**:
  - *Context*: Downstream projects keep project-specific checks (canonical literals, house conventions) in bespoke scripts because omnicoach rules are compiled in. Deny-list options on generic rules (banned calls and `adhoc-type-annotation` for banned composite type annotations) are configurable today.
  - *Candidates to compare*: (a) more generic rules driven by configurable pattern lists (banned literals); (b) declarative pattern rules in `.omnicoach.toml` (ast-grep-style YAML patterns, or a query language over the existing `ruff_python_ast` / `ra_ap_syntax` trees, which have no built-in query language unlike tree-sitter); (c) a plugin API (Python or WASM). Compare expressiveness, `--explain` documentation, testability (an equivalent of `rule_test!` for user rules), suppression support, and performance. Running ast-grep (`sg scan`) directly in the downstream project is the zero-cost baseline.
  - *Trigger*: When a downstream project needs a rule that is too project-specific to ship in omnicoach and too structural for a deny list.
- **Rule Autofix Engine (`diffy` / `similar`)**:
  - *Target*: Extend `CodeRule` and `CommandRule` with optional auto-fix transformations. Support `--fix` and `--fix --dry-run` with in-memory unified diff previews before writing changes to disk.
  - *Trigger*: When implementing the first batch of auto-fixable rules (e.g., replacing `logging.error` with `logging.exception`).
- **Generic Container Base-Type Matching (`identical-positional-types`)**:
  - *Current*: Positional parameter types are compared by exact formatted annotation string (`dict[str, int]` != `dict[str, float]`).
  - *Target*: Optionally normalize or group generic collection/mapping containers (`dict[...]`, `Mapping[...]`, `list[...]`, `Sequence[...]`) so multiple positional mappings or sequences are flagged even when their inner type arguments differ. Equivalent spellings of one type (`Optional[str]` vs `str | None`, `List[int]` vs `list[int]`) are also compared as different today.
- **Escaping Nested Scopes (`environment-variable-in-function`)**:
  - *Current*: The boundary exemption (`main`, `from_env`, ...) is inherited by every scope declared inside it, which is correct for nested functions and closures but also exempts a class declared inside a boundary whose methods later escape (returned, registered as a callback).
  - *Target*: Treat a `class` / `impl` declared inside a boundary as a barrier that resets the exemption, once a real-world occurrence justifies the added language-specific complexity.
- **Import-Aware Qualified Call Resolution (`src/code_lint/ast/imports.rs` & `src/code_lint/semantic/calls.rs`)**:
  - *Current*: Literal banned-call entries, dedent wrappers, decorators, class bases, and collection annotations are resolved through a per-file import map (`ast::resolve_name`): an imported name matches only by its canonical path (`import typing as t; t.cast(...)` matches `typing.cast`; `from sqlalchemy import cast` no longer matches `cast`), a module-level definition never matches, and an unimported name matches as written. Only module-level Python imports and root-level Rust `use` items are considered; imports inside functions or `mod` blocks, function parameters, assignment aliases, and the receiver of `<callee>().<method>` entries are not resolved.
  - *Target*: Evaluate scope-aware resolution (nested imports, parameter/fixture receivers such as `mocker.patch`, `monkeypatch.setattr`, `loop.create_task`, and context-manager aliases such as `with pytest.MonkeyPatch.context() as mp: mp.setattr(...)`), modeled on Ruff's `SemanticModel::resolve_qualified_name`.
- **Dependency-Aware Rule Activation (`pyproject.toml` / `Cargo.toml`) & Loguru Format Enforcement (`LoggerPrintfFormatRule`)**:
  - *Context*: Some rules only make sense when a project uses a specific library ecosystem. The legacy linter's `LoggerPrintfFormatRule` targets `loguru`: while `"..." % ...` is covered by Ruff `G002` (`logging-percent-format`) and `UP031` (`printf-string-formatting`), multi-argument `logger.info("User %s", user)` is required in stdlib `logging` (enforced by Ruff `G001`–`G004`), yet in `loguru` it is a silent data-loss bug (`str.format` ignores unused positional arguments when no `{}` is present; today only Pylint `E1205` with `[tool.pylint.logging] logging-format-style = "new"` and `logging-modules = ["loguru"]` checks this).
  - *Target*: Investigate dependency-aware rule activation (inspecting `pyproject.toml` / `uv.lock` / `Cargo.toml` or project-wide imports) or a configurable logging format mode so a `printf-log-format` rule enforcing `{}` placeholders over `%s` in logger calls can be enabled automatically when `loguru` is installed. (Implementation note: unparenthesized printf regexes must exclude the `' '` space flag so ordinary English percentages like `"100% complete"` or `"50% discount"` do not match `% c` / `% d`.)
- **Rule test harness (`rule_test!` in `src/test_utils.rs`)**:
  - *Repeat check vs. scope-wide rules*:
    - *Current*: every `fail` case also runs as `{code}\n{code}` in one module and must report exactly the two copies' spans. The second copy redefines every top-level name, so a rule that reasons about the other definitions in a scope sees a different program than the case states. For module-level declaration-order rules such as `statement-after-main-guard`, any statement preceding the first `if __name__ == "__main__":` guard in the snippet appears after the first guard in the second copy, so `fail` snippets must start with the guard.
    - *Target*: a repetition that stays strict for these rules. Candidates: a `RepeatCheck::DistinctNames` variant, modeled on `DistinctLiterals`, that renames the second copy's definitions and their references (solves redefinitions, not ordering); isolating each copy in its own scope where the language allows it (a Rust `mod`; Python has no equivalent that keeps module semantics); or requiring both copies' spans to be among the findings rather than equal to them (fits ordering rules, weaker). Today's escape hatch is a unit test on the collector (`rule_test!` docs, "Writing cases").
  - *Multi-diagnostic `fail` cases*: a `fail` case expects exactly one span, so 3+ copies and a constant plus two uses are only unit-tested on the collector (`repeated-literal`). A `fail` case listing several spans would cover them (also needed by `nested-function`).
  - *Exemption & branch adequacy verification (post-`scripts/exemptions/`)*:
    - *Current*: `run_code_rule` rejects syntax errors in `rule_test!` snippets (`!parsed.has_syntax_error()`), and rule/helper branch adequacy is verified on changed files via `cargo mutants --in-diff` (or `cargo mutants -f <path>`) and `cargo +nightly llvm-cov --lib --branch`.
    - *In-memory option checks*: For exemptions owned by the rule declaration (`ListOption` allowlists, `CountOption` thresholds), `rule_test!` could automatically re-run `pass` cases with options tightened in-memory during `cargo test`.
    - *Shared-extractor exemption blind spot (investigate)*:
      - *Problem*: When an exemption is implemented inside a shared `ast/` or `semantic/` helper used by multiple rules (e.g. `BindingKind::Import` in `semantic::bindings`, `is_interface_method` in `ast::python::functions`, `is_in_rust_inline_test` in `ast`), `cargo mutants -f src/code_lint/rules/<rule>.rs` does not mutate the shared helper, while mutating the shared helper itself is killed as soon as *any one* consumer rule (or unit test) fails. As a result, a vacuous `pass` case for that shared exemption inside a *second* consumer rule's `rule_test!` is not caught by either `llvm-cov --branch` or `cargo-mutants`.
      - *Candidates to evaluate*: (a) **Single-layer test ownership ([ADR 012](docs/dev/decisions/012_module_placement_by_abstraction.md))**: test shared-extractor exemptions once in unit tests on the `ast/` or `semantic/` module that defines the contract (matching how `require-explanation` is tested once in `semantic::comments`), pruning duplicate extractor-level `pass` cases from individual rules; or (b) **Opt-in input-contrast edits in `rule_test!`**: allow `pass` cases that rely on a shared helper to specify an optional in-memory snippet replacement (`name ("old" => "new") => "code"`) asserting that the modified snippet triggers the rule during `cargo test`.
  - Related: "Examples for suppression audits" (§5).
- **Rule dependencies and soundness**:
  - *Status*: Understood and explored: [01_understand.md](docs/dev/rule_dependencies/01_understand.md), [02_references.md](docs/dev/rule_dependencies/02_references.md), [03_design.md](docs/dev/rule_dependencies/03_design.md). Both committing to a design and implementing it are deferred until a larger rule corpus lands, so we do not overfit the abstractions to an early subset of Omni ↔ Omni edges (D13).
  - *Context*: Rules relate through detection (`Partitions`, `Equivalent` / `Subsumes` / `Overlaps`), fixes (`Chain`, `Cycle`, `Contradiction`, `DivergentAdvice`) and soundness (`ReliesOn`, `Delegates`). These relations live only in prose, and nothing checks that one rule's fix does not trigger another rule.
  - *When resumed*: Do not blindly implement `03_design.md`. Re-inventory the expanded rule corpus, challenge the prototype findings (`Partition` constants, active-voice edges, `Concept` intermediates, compile-time rule names, executable witnesses, and the Option D fix-conflict harness), and look for simpler or stronger abstractions before committing (`03_design.md` §4).
  - Related: "Typed overlap / sources field" (§5).

### Candidate Rules & Rule Follow-ups

Candidates and known-gap follow-ups to prioritize, not commitments. Evaluated candidates that were intentionally not pursued (and the external linter configurations that cover them) are recorded in [docs/dev/not_pursued_rules.md](docs/dev/not_pursued_rules.md).

- **`repeated-index-access` follow-ups** (Python, Rust):
  - *Macro arguments*: reads inside expression-like macros (`format!`, `assert_eq!`, `vec![]`) are not inspected because `ra_ap_syntax` leaves them as flat `TokenTree` tokens (pass case `known_gap_macro_arguments_not_inspected`). Supporting them needs a multi-token span in `AstNode` (`cmd.span.0` is several tokens, not one node) or re-parsing the arguments as expressions.
  - *Receiver rebinding*: `a = p[0]; p = nxt(); b = p[1]` groups two different values as one receiver (both languages). Needs binding awareness (split the group at each rebinding).
  - *Shadowing*: a closure parameter (`|t| t.1`) or comprehension variable reusing the receiver's name is grouped with the outer receiver (both languages).
  - *Receiver normalization*: receivers are grouped by source text, so `(t).0` vs `t.0`, `len((xs))` vs `len(xs)`, and chains split across lines are not recognized as the same receiver.
- **Signature & attribute collection type rule follow-ups** (`concrete-collection-*`, `mutable-collection-*`, `specific-collection-parameter`, `nullable-collection-return`):
  - *Type alias resolution*: `type IntList = list[int]` or `IntList: TypeAlias = list[int]` used in annotations is treated as an unknown generic/identifier until per-file type-alias resolution is added.
  - *Cross-file caller and subclass mutation tracking*: return and attribute mutation checks (`collect_locally_mutated_return_functions`, `collect_public_class_attributes`) operate within a single file; cross-module mutations rely on the default `require-explanation` mode.
  - *String annotation resolution*: string annotations (`"list[int]"`) are not parsed (pass case `known_gap_string_annotation_not_parsed`). Import aliases are covered by "Import-Aware Qualified Call Resolution".
  - *Callee resolution for returned values*: `collect_locally_mutated_return_functions` matches callees by bare name, so mutating `cfg.get(...)` exempts every function named `get` in the file (pass case `known_gap_same_named_callee_exempts_function`).
  - *Header-wide explanation scope*: one `RequireExplanation` comment above a `def` silences every finding on that header, across rules. Framework-wide behavior; per-rule scoping would need comment-to-rule association.
- **Declaration ordering follow-ups** ([ADR 011](docs/dev/decisions/011_colocated_abstraction_ordering.md)):
  - *Bindings inside Rust macros*: macro arguments are unparsed tokens, so a bare identifier there that matches a sibling `fn` counts as a reference. This is needed for functions passed as values (`matches!(e, X(v) if v.iter().any(helper))`), but a pattern binding or named argument with the same name (`matches!(x, Some(value) if value > 0)` next to `fn value`) creates a false call edge. Telling them apart needs the macro arguments parsed as expressions or patterns. `self.field` inside a macro is already told apart from `self.method(...)`.
  - *Constructors run by definition-time instantiation* (Python): `ScopeGraph::evaluated_before` propagates bounds only through `RelationKind::Body` edges, so a class instantiated while the module body runs (`INSTANCE = _Service()`) does not bound the helpers its `__init__` / `__new__` call. `private-before-public` then suggests moving such a helper below the public consumer, which makes the instantiation raise `NameError` at import. Following `Behavior` edges into all methods would wrongly exempt helpers used only by methods of a base class. The fix needs the module-level type item to expose its constructor callees as a distinct relation, followed only when the type itself is called at definition time.
  - *`Annotated` metadata over-approximation* (Python): under postponed annotations, helpers referenced in PEP 593 `Annotated` metadata (including PEP 695 `type` alias values) are treated as evaluated at definition time whether or not a runtime-introspecting library (Pydantic, FastAPI, …) consumes the annotation, so the exemption also applies to plain functions and aliases nothing introspects. Narrowing it would need to know which classes and functions are introspected (for example `pydantic.BaseModel` subclasses or FastAPI route decorators).
- **`repeated-literal` follow-ups** (Python, Rust):
  - *Values inside exempt macros* (Rust): the whole exempt macro (`assert_eq!`, `format!`, …) is skipped, so `assert_eq!(x, "expected")` repeated in production code is not counted (pass case `known_gap_values_inside_exempt_macros`). Counting only value arguments needs per-macro knowledge of which arguments are format strings.
  - *Negative numbers as separate tokens* (Rust): inside a macro `token_tree` the sign is a bare `-` token, so the number is skipped rather than counted as `N` (pass case `known_gap_negative_numbers_in_macros`).
  - *Unpacked and chained constants* (Python): `A, B = 1, 2` and `A = B = 1` are not recognized as constant definitions; their values count as inline uses.
  - *Typed template placeholders*: constants such as `CALLEE = "callee"` exist only to name a template placeholder once. A typed placeholder (enum or typed key) would remove them.
  - *Multi-diagnostic `rule_test!` cases*: see "Rule test harness".
- **Import alias conventions** (`import x as y`, `use x as y`):
  - *Context*: Naming rules (`single-letter-name`, `abbreviated-name`, `type-suffixed-name`, `primitive-duration`) skip all imports, including aliased imports.
  - *Investigation*: Evaluate how much is already covered by Ruff's `flake8-import-conventions` (`ICN001` `unconventional-import-alias`, `ICN002` `banned-import-alias`) and Pylint (`PLC0414` `useless-import-alias`), and whether a dedicated multi-language import-alias rule is warranted in Omni.
- **`error-log-in-except` vs. Ruff `TRY400` (`error-instead-of-exception`) & `G201` (`logging-exc-info`)**:
  - *Status*: Kept, with the overlap documented in the rule's `known_problems`. Measured against Ruff 0.17.0: with the default deny list, every call the rule flags is also flagged by `TRY400` (plain or `exc_info=False`) or `G201` (`exc_info=True`). Ruff additionally flags name-guessed logger objects (`logger.error`, `response.log.error`) and calls inside functions or lambdas defined in the `except` block, which usually run after it, where `logging.exception` logs `NoneType: None` instead of a traceback.
  - *Open*: whether to broaden the default deny list to import-resolved logger objects (`loguru.logger.error`) once the template suggestion names the flagged object's own `.exception` method instead of always `logging.exception(...)`.
- **Rules needing a project-wide symbol or call index** ([03_design.md](docs/dev/protocol_inheritance/03_design.md); project model in [docs/dev/project_linting/03_design.md](docs/dev/project_linting/03_design.md)):
  - *Implemented on `CodeLintProject`*: `uninherited-protocol` now resolves `Protocol`s imported from first-party modules (following re-export chains, `__all__`, and `.pyi` stub precedence) via `ProjectContext::imported_protocols_in_module`.
  - *Architecture-aware cross-file rules*: `uninherited-protocol` already matches only `Protocol`s the linted file explicitly imports (or defines locally), so it never suggests adding a new cross-module dependency; if future cross-file rules suggest unimported symbols across modules, filter candidates against the active `ArchitectureSpec` so a rule never suggests a dependency across a forbidden component boundary.
  - *Unused `Protocol` / `ABC` method* (legacy `UnusedInterfaceMethodRule`): a method never called anywhere in the project. Needs a type-aware call index: bare attribute-name matching misses `Protocol.get` / `read` / `run` whenever any `dict.get()` or `file.read()` exists, and flags `getattr` dispatch, framework callbacks and public library interfaces. A single-file version would flag nearly every interface method ([01_understand.md](docs/dev/protocol_inheritance/01_understand.md) §1.3).
  - No Rust counterpart: traits require an explicit `impl Trait for Type`.
- **Docstring rule follow-ups (`docstrings` topic)**:
  - *Cross-file base-class & C3 MRO resolution (implemented)*: `copied-base-docstring`, `partial-override-docstring`, and `deferral-docstring` now resolve cross-file base classes and inherited method docstrings in C3 MRO order via `ProjectContext` (`src/code_lint/project/context.rs`).
  - *Cross-file caller/subclass mutation tracking*: extending `ProjectContext` with cross-module call/mutation facts would unlock cross-file caller and subclass mutation tracking for collection signature rules (`concrete-collection-*`, `mutable-collection-*`).
- **`abbreviated-name` follow-ups** (Python, Rust):
  - *Positional / boundary matching (`c_` vs `_c`)*: allow entries with a trailing underscore (e.g. `c_`) to match only prefix/infix segments (`c_val`, `foo_c_bar`) while allowing suffix (`foo_c` / `FooC`), and entries with a leading underscore (e.g. `_c`) to match only suffix/infix segments while allowing prefix (`c_val` / `CVal`).
  - *Acronym-to-word CamelCase splitting in `split_segments`*: split uppercase-to-uppercase-followed-by-lowercase transitions (e.g. `DBConnection` → `["db", "connection"]`, `HTTPRequest` → `["http", "request"]`); currently `split_segments` only splits on lowercase/digit → uppercase.
  - *Default banned abbreviations*: evaluate adding `"db"`, `"mgr"`, `"util"`, `"conn"`, `"expr"` to `abbreviated-name`'s default list.
- **`jj` history & parallel multi-workspace safety rules (`command_lint` + `hook`)**:
  - *Block file edits when `@` is a described, non-conflicted commit*: when a file-write tool runs in `omnicoach hook` and `@` already has a non-empty description (and no conflicts), deny the edit so the agent creates a new draft change (`jj new`) instead of mutating committed history.
  - *Parallel `jj` workspace safety rules* (sharing read-only revset `(<set>) & mutable() & ::(working_copies() ~ @)` run with `--ignore-working-copy`):
    - **Block rewriting a commit another workspace builds on**: map rewriting subcommands (`edit`, `describe`, `abandon`, `squash` `--from`/`--into`, `rebase -r/-s/-b`, `split`, `restore --into`, `absorb`) to their target commits; `deny` when a target is another workspace's `@`, `force_ask` when another workspace builds on it.
    - **Block `jj fix` when it rewrites another workspace's `@`**: `force_ask` when `reachable(@, mutable())` overlaps another workspace's `@` or its mutable ancestors.
    - **Block pushing/uploading a shared base or divergent change**: `force_ask` when the target mutable ancestor set contains a commit another workspace builds on; `deny` when it contains a divergent change (checked via template `if(divergent, change_id ++ "\n")`).
  - *Non-interactive & trailer-preserving description updates on `jj describe` / `jj commit` / `jj squash`*:
    - Block bare interactive `jj describe`, `jj squash`, and `jj split -i` (which open an editor and hang in non-interactive agent sessions).
    - Block `jj squash -m` when the destination commit already has a description (require `jj squash -u`).
    - Optionally preserve configured commit trailers when updating an existing commit description.
  - *Block unbounded `jj log` queries (`unbounded-jj-log`)*:
    - Bare `jj log` defaults to `revsets.log` (bounded), whereas passing `-r` / `--revision` or positional fileset paths has no built-in `--limit` config in `jj` and walks immutable mainline history (`::trunk()`) when unscoped—in monorepos, open ranges like `x..` (`~::x`, which includes `x..trunk()` once `trunk()` advances past `x`), `<immutable_base>::`, `::@`, or bare `mine()` evaluate tens of thousands of commits (amplified when templates call `diff.summary()` or `-p` / `--stat` fetches per-commit trees).
    - **Allow**: bare `jj log` (no `-r` and no positional filesets), commands with an explicit `-n` / `--limit` (optionally capped by a configurable `max-limit`, e.g. `1000`), point or local-neighborhood revsets (`@`, `<rev>`, `a | b | children(c)`, `parents(x)`), and any `-r` intersected at the top level with `mutable()`.
    - **Deny** (suggesting `& mutable()` or `--limit <N>`): positional fileset filters (`jj log <path>`) without `--limit` or `-r` scoped to `mutable()`, and `-r` expressions using range/complement operators (`..`, `::`, unary `~`) or global sets/predicates (`all()`, `visible()`, `immutable()`, `mine()`, `author()`, `committer()`, `description()`, `subject()`, `files()`, `diff_lines()`, 1-arg `ancestors(x)` / `descendants(x)`) without top-level `& mutable()` or `-n` / `--limit`.
    - *Design trade-off to evaluate (`x::`)*: purely syntactic checking runs in under 1 ms with zero `jj` subprocesses and requires `<rev>:: & mutable()` or `--limit`, whereas querying `JjClient` (`--limit 1 -r <x> -T immutable`) permits bare `<mutable_rev>::` while still rejecting `<immutable_base>::` / `p4base::` at the cost of a subprocess call and expression-root extraction.
  - *Enforce subcommand before global flags (`subcommand-before-global-flags`)*: flag subcommand CLIs (`jj`, `git`, `cargo`, `uv`) invoked with global flags ahead of the subcommand (e.g. `jj --no-pager log`). Leading flags break index-`0`/`1` token-prefix matching in coding-agent permission engines and force full-command grants.
- **Shell & agent command rules (`command_lint`)**:
  - *Executable existence check*: verify that each invoked command executable exists in `PATH`, exists as an executable path relative to `Cwd`, or is a shell builtin.
  - *Block redundant shell wrappers (`bash -c`, `sh -c`, `zsh -c`, `eval`)*: when the agent runner already executes in `bash`, wrapping commands in `bash -c "..."` or `eval` breaks prefix-based auto-approval, causes nested-quote `$VAR` bugs, and hides inner commands.
  - *Block shell file-reading/editing, URL-fetching, and inline Python (`python3 -c`)*: reject `cat`, `head`, `tail`, `sed`, `curl`, `wget`, `tee`, heredoc/redirection writes to workspace files, and `python`/`python3 -c "..."`, steering agents to dedicated file/HTTP tools or a reusable script in `scratch/`.
  - *Enforce single-command prefix-approvable shapes when sandbox bypass is requested*: warn/deny commands with unquoted pipes (`|`), command substitutions (`$(...)`), leading `VAR=val` env prefixes, or multi-command chains (`&&`, `;`, `\n`) when sandbox bypass is enabled.
  - *Configurable banned command / API patterns*: project- or profile-configured command replacements (e.g. steering raw build/search invocations to agent-friendly wrappers).
  - *Markdown link formatting*: ban `file:` scheme in Markdown file links (`[label](file:///...)` in `.md` files) and backticks inside Markdown link brackets (`` [`label`](...) ``).

## 2. Performance & Concurrency Architecture

- **Single-Pass Rust CST Extraction to Eliminate Rowan Red-Tree Cursor Allocation Multiplication**:
  - *Status*: **Measured, deferred** (O3). Each Group E Rust rule costs about one full Rowan walk (~850 µs / 18.6k allocations per `descendants_with_tokens()` pass over the 49 KB Rust fixtures). End to end, cargo 0.100.0 takes 2.6 s CPU / 0.48 s wall, so fusing the walks would save a fraction of that. Revisit with a dedicated prototype when large Rust repositories are a target.
  - *Context & Empirical Measurement*: On `rs_real_ast_module` (`annotations.rs`, 23.6 KiB), `linter::end_to_end_all_rules` takes `4.84 ms` and performs **46,843 heap allocations (2.22 MB)**; across the 4 Rust fixtures, `E_dedicated_extractors` accounts for **78.0% of warm Rust rule time (`6.28 ms`) and 68,726 heap allocations (2.76 MB)**.
  - *Root Cause*: `ra_ap_syntax` uses Rowan's green/red tree. Unlike `ruff_python_ast` (where AST nodes live in contiguous `Vec`/`Box` slices and traversing them allocates 0 bytes), each call to `syntax.descendants()` or `syntax.descendants_with_tokens()` on a Rowan `SyntaxNode` dynamically allocates heap-backed red-node cursors (`4,400–8,800` heap allocations per full-file walk on `annotations.rs`). Today, 4 `OnceLock` extractors and 6 Group E rules each perform their own independent `syntax.descendants()` walk.
  - *Target*: Fuse the Rust CST extractors (`call_candidates`, `bindings`, `comment_nodes`, `rust_inline_test_ranges`, `literal_occurrences`, `positional_reads`, `find_unwrapped_multiline_strings`, `collect_functions`, `collect_test_function_assertion_counts`, `collect_test_to_test_calls`) into a single top-down `syntax.descendants_with_tokens()` visitor pass per file so the Rowan red-tree is materialized only once. Red nodes cannot be cached on `ParsedFile` (`SyntaxNode` is `!Send`/`!Sync`).
- **Workspace-Wide Rule Performance: Rust vs. Python & External Crate Attribution (Investigate)**:
  - *Context & Empirical Observation*: On Python corpora (`CPython Lib` and `gauge-sh/tach`), workspace-wide rules add `1.14x–1.20x` CLI wall time and `5.4–6.7 ms` agent-hook latency ([04_review_and_learn.md](docs/dev/project_linting/04_review_and_learn.md)). On external Rust crates without `src/architecture.rs` (`ripgrep`'s `crates/ignore/src/dir.rs`), probing only the `architecture` module keeps cold `omnicoach hook` latency at `45 ms` median (`54 ms` p90, vs `52 ms` median on `main@origin`). On `omnicoach` itself (`140` `src/*.rs` files, active 24-component `define_architecture!` in `src/architecture.rs`), CLI wall time is `241 ms` vs `186 ms` single-file (`+55 ms`, `1.30x`) and cold `omnicoach hook` latency on `src/config.rs` is `30 ms` median (`32 ms` p90, vs `11 ms` on `main@origin`), dominated by scanning and parsing candidate Rust module headers across `src/`.
  - *Investigation & Design Questions*:
    - How do workspace-wide rules perform on external Rust crates (`ripgrep`, `cargo`, `tokio`) both with and without `.omnicoach.toml` `[architecture]` enabled, compared to `omnicoach` itself and to Python repositories of equivalent size?
    - Where does the Rust time actually go across (a) `ra_ap_syntax` CST parsing and Rowan red-tree cursor allocation vs `ruff_python_ast`, (b) full-file `summarize_rust_file` vs body-free `summarize_rust_module_header` (and whether full-body CST summarization is needed when module headers or existing `ParsedFile` `OnceLock` facts suffice), and (c) cold-start `ProjectIndex` discovery during single-file `omnicoach hook` runs (where `rust_headers_map()` currently walks `src/` for macro candidates when `architecture` declares `define_architecture!`, whereas 5 of the 8 Rust `Topic::ARCHITECTURE` rules only need ancestor `mod.rs` headers + `src/architecture.rs`)?
    - Can Rust architectural conformance and cross-file queries reuse the `ImportMap` and single-pass CST facts already computed on `ParsedFile` rather than running a separate `summarize_rust_file` traversal?
  - *Measured Breakdown (`omnicoach hook`, one clean edit on `omnicoach`)*: of a ~`35–41 ms` single lint pass, `rust_headers_map()` takes ~`29–32 ms`: walking `src/` (`185` files) ~`5 ms`, reading and prefiltering files ~`8 ms`, and parsing the ~`30` candidate headers with `ra_ap_syntax` ~`16–18 ms` on 16 threads (`45 ms` on one thread). Header parsing is the largest single cost, so reducing it needs either fewer bytes parsed per candidate (a lexer-level header scan) or reuse across runs, not a narrower text prefilter (which cannot be sound).
- **Remaining Serial Time in End-to-End Runs**:
  - *Context*: CPython 3.14.8 takes ~1.4 s wall for ~7.3 s of CPU on 16 cores (ideal ≈ 0.5 s).
  - *Investigation*: Attribute the serial part between directory discovery (see the directory item below), the final sort, and diagnostic formatting before changing anything.
- **Suppression Fast-Path False Trigger on `"omni:"` Inside String Literals**:
  - *Context & Empirical Measurement*: `SuppressionTracker::from_file` runs at `7.8–15.9 GB/s` with `0` allocations when `"omni:"` is absent, but on `rs_real_test_suite` (`tests/cli.rs`) the substring appears inside test string literals, so the fast path falls through to `collect_comment_nodes` (`521 µs`, `2,213` allocations).
  - *Investigation*: Not pursued yet (O4): no measurement shows it mattering on real repositories. The fallthrough is correct, only slower, and a narrower pre-check (e.g. `"omni:disable"`) must not miss any valid directive.
- **Repeated Python function-signature and class extraction (`extract_function_signatures`, `extract_classes`, `enclosing_class`)**:
  - *Current*: Unlike `bindings` and `call_candidates` (memoized on `ParsedFile` via `OnceLock`), `extract_function_signatures(file)` and `extract_classes(file)` walk the Python AST fresh on each call (11 and 8 callers per file respectively), and `ast::python::is_interface_method` calls `enclosing_class(signature)`, which rebuilds `PythonClassInfo` (import resolution of every base and decorator, docstring) for each method it is asked about. Each fact has a single derivation, so this costs time, not correctness.
  - *Target*: If a benchmark shows it matters, build each function signature and class once per file (for example by memoizing span-only representations on `ParsedFile` or sharing one `PythonClassInfo` per `class` statement).
- *Evaluation protocol for the items above*: each change ships only with a before/after `omni_bench` run on the pinned fixtures (median time + allocation counts) plus an end-to-end `hyperfine` run; any change that adds complexity (new caches, fused visitors, new data on extracted structs) needs a measured win that justifies it, prototyped on its own branch first.
- **Directory Discovery Parallelism & Micro-Run Overhead**:
  - *Current*: File-level analysis runs in parallel via `rayon` (`targets.into_par_iter()`) with deterministic sorting across both plain-text and JSON output, while directory traversal in `collect_directory_candidates` runs single-threaded via `ignore::WalkBuilder::build()`.
  - *Investigation*:
    - Evaluate whether `ignore::WalkParallel` improves directory discovery on large repositories compared to single-threaded collection + `rayon`.
    - Measure `rayon` thread-pool initialization overhead on small repositories to ensure micro-runs and pre-commit hooks are not penalized.
- **Subprocess Batching & Caching (`EnvContext`)**:
  - *Current*: Command rules spawn individual `jj` or `git` CLI calls per evaluation.
  - *Target*: Introduce a shared `EnvContext` struct that pre-fetches and caches repository state (e.g., batching queries into a single `jj log --json` or `git status` invocation) to ensure sub-10ms execution across multiple rules.
- **VCS Error Propagation**:
  - *Current*: VCS client query errors in command rules are swallowed to avoid blocking users on query failures.
  - *Target*: Propagate structured errors or display user warnings when the underlying VCS client fails unexpectedly, distinguishing clean working copies from failed CLI calls.

It serves `explain`, `catalog`, and single-file `lint` (`code_lint::runner::lint_file`, so `ProjectCodeRule`s render in the catalog and `--explain` while skipping live single-file buffers) through [playground/www/omnicoach.js](playground/www/omnicoach.js).
  - *Target*:

    - Expand `playground/www/` to preview shell command rules (via `wasm32-wasip1` with a minimal JS WASI shim or upstream feature gates in `brush-parser`) and single/multi-file architecture graphs.
- **Abstraction Graph & Structural Formats for AI Coding Agents (Alpha / Experimental)**:
  - *Status*: **Alpha — under active investigation & design** ([01_understand.md](docs/dev/abstraction_graph/01_understand.md) through [13_stage_e_diagnostic_placement_design.md](docs/dev/abstraction_graph/13_stage_e_diagnostic_placement_design.md)). Implemented in `src/code_lint/project` (`CodeLintProject`: source discovery, project layout, `ArchitectureSpec`, and `ProjectIndex`) and `src/code_lint/graph` (`CodeLintGraph`: `ProjectFacts`, model, builder, renderers, and queries), and exposed via the alpha/experimental `omnicoach graph [PATHS...] [--depth module|public|full] [--no-signatures]` CLI and bounded query subcommands (`find`, `slice`). Everything in this area—the graph model, grouping rules, output syntax, and CLI surface—is experimental and may change or be replaced at any time.
  - *Context & Architecture*: `omnicoach` computes intra-module declarations, entrypoint ownership (`Roots(h)`), typed abstraction ordering ([ADR 011](docs/dev/decisions/011_colocated_abstraction_ordering.md)), recursion groups (SCCs), and project-level architectural conformance ([ADR 006](docs/dev/decisions/006_architectural_dag_and_conformance.md)). `CodeLintGraph` extracts multi-file `ProjectFacts` (`src/code_lint/graph/facts.rs`, backed by `CodeLintProject` in `src/code_lint/project/`, `86.6%` exact SCIP symbol-to-symbol recall, `100.0%` cross-module `Type::method` target recall, `98.4%` literal precision in `0.46 s`) and builds a validated `AbstractionGraph` (`model.rs`) $\to$ canonical `P3_members` builder with 3-scale levelization and 3-way Reflexion status `Convergent`/`Absent`/`Divergent`/`Inferred` (`builder.rs`) $\to$ text format renderers (`render.rs`) and bounded query engine (`query.rs`).
  - *Investigation Findings So Far*:
    1. **Visual node-link graphs vs. text formats (`Stage B M4`, 24 questions × 4 conditions)**: Interactive/rendered node-link diagrams (`Cytoscape.js + ELK`, `GraphML`, `DOT`) are useful for human top-level component overviews, whereas `VisualOnly` agents scored `14.25 / 24 (59.4%)` and needed `4.5×` more steps than text (`OutlineOnly` scored `24.0 / 24 (100.0%)` in `8` steps vs `RawCode`'s `23.5 / 24 (97.9%)` in `46` steps).
    2. **Candidate AI agent formats (`Stage C`, 24 tasks × 4 formats = 96 isolated runs)**: Comparing `F1_Outline` (Stage B baseline, `18.0 / 24 = 75.0%`), `F2_CompactBi` (`21.25 / 24 = 88.5%`), `F3_AnnotatedStubs` (`24.0 / 24 = 100.0%`), and `F4_StructuredYaml` (`24.0 / 24 = 100.0%`) showed:
       - **Bidirectional edges (`-> uses` and `<- used_by`)** with module-qualified cross-file targets (`module::symbol`) cut agent navigation steps in half (`6` steps vs `13` steps) and reduce line count by `38.8%`.
       - **Declaration end lines (`:start..end`)** raise 1-step ADR 011 refactoring & placement planning accuracy from `56.3%` to `100.0%`.
       - **Inline 1-line signatures + type field summaries (`F3_AnnotatedStubs`)** raise Zero-Read API Synthesis on unfamiliar code (`omnicoach`) from `25.0%` to `100.0%` at `27.2%` of raw source bytes (`-21.0%` lines vs `F1_Outline`), whereas verbose YAML (`F4_StructuredYaml`) buys zero accuracy at `+45.6%` more bytes and `+91.8%` more lines.
    3. **Live coding-agent benchmark & query subcommands (`Stage D`, 84 isolated subagent runs + follow-ups across 6 tasks and 2 model tiers)**:
       - **Statistically significant trajectory efficiency & comprehension gains**: Bounded query subcommands (benchmarked as `find`, `slice`, `place`, `impact`; `place` and `impact` were later removed in favor of `omnicoach code` diagnostics, see [05_decisions.md](docs/dev/abstraction_graph/05_decisions.md) `D63`) reduced cost-weighted tokens by **`-38.4%` (`95% CI [-50.5%, -25.0%]`)** across the 6 primary tasks (`-42.2%` across all 84 runs, `-52.4%` on `flash` with Turn-1 invocation), cut pre-edit search/read calls by **`-52.5%`**, and raised open-ended architectural comprehension accuracy from `83.3%` (`flash`) / `91.7%` (`inherit`) to **`100.0%`**—enabling `flash` + Query CLI (`473K` tokens, `374 s`) to beat `inherit` without the graph (`579K` tokens, `429 s`).
       - **Scope-disjoint tool selection & target-dependent default depth**: Single-file `omnicoach graph <file>` wins when the target file is already known and requires multi-hop intra-file call-hierarchy comprehension (`-76.0%` tokens on Tarjan SCC bugfix, `-67.0%` on `ripgrep`), whereas `find` / `slice` win on cross-module discovery and repository comprehension, and `omnicoach code` diagnostics give the conflict-free ADR 011 insertion anchor. Without `--depth`, a single file renders at full depth and a directory or several files at module depth; module-depth graphs above `20` modules omit per-module edges with a notice line, and peer lists and empty-module lists are capped visibly (`... (+N more)`). Together with the shared `8 KB` `slice` budget, this keeps default outputs below the `10 KB` agent-harness inline stdout truncation cliff.
  - *Follow-ups & Open Questions*:
    1. **Additional cross-file lint rules on `CodeLintProject`**: `CodeLintProject` (`src/code_lint/project`) now powers the 8 native `Topic::ARCHITECTURE` conformance rules, cross-file `uninherited-protocol`, and cross-file C3 MRO docstring inheritance (`copied-base-docstring`, `partial-override-docstring`, `deferral-docstring`; see [docs/dev/project_linting/03_design.md](docs/dev/project_linting/03_design.md)). Remaining cross-file rule candidates:
       - Intra-component module dependency cycle detection.
       - Cross-module dead-abstraction / unused-public-item detection (unused `public-exports` and unused `Protocol`/`ABC` interface methods).
    2. **Local parameter & `let`-binding receiver-type resolution for `x.method()` calls**: Cross-module `Type::method` and intra-module `Self::method` paths are now resolved at `100.0%` recall, leaving receiver-typed method calls on local variables (`tracker.is_suppressed()`, `node.children()`, `376 / 3,933 = 9.6%` of SCIP edges) and trait dynamic dispatch (`150 / 3,933 = 3.8%`) as the only remaining static call-graph gap. Add lightweight local type-binding resolution in `ScopeFacts` for explicit function parameter annotations (`fn foo(tracker: &SuppressionTracker)` / `def foo(tracker: SuppressionTracker)`) and simple constructor bindings (`let x = Type::new(...)` / `x = Type(...)`) so receiver-typed method calls resolve to `Type::method` without requiring a full compiler type-checker or sacrificing the `98.4%` precision floor.
    3. **Flat utility-hub cohesion signal**: When `shared_groups / owner_groups` is high in a module (a horizontal utility hub where many public entrypoints share distinct subsets of private helpers), evaluate surfacing that cohesion ratio in the module header or as an informational architectural hint.
- **On-Demand Suppression / Explanation Comment Placement Hint**:
  - *Context*: When a diagnostic spans an inner node (e.g. a function or parameter name inside a multi-line signature, a decorated declaration, or a statement inside a block), it is not always obvious which lines `SuppressionTracker` accepts for an `# omni:ignore[rule] -- reason` directive or a `RequireExplanation` comment. At the same time, including suppression instructions in the default diagnostic output would clutter every finding and nudge authors/agents toward suppressing instead of fixing.
  - *Investigation*: Explore an opt-in mechanism (such as a CLI flag, `--format json` metadata field, or query subcommand) that reports the valid comment insertion line(s) for a diagnostic without showing it in default terminal messages.
- **Feature-Gated Rich Terminal Diagnostics (`miette`)**:
  - *Current*: Fast, zero-dependency printer in `src/diagnostic.rs` outputting standard compiler-style format (`path:line:col: [CODE] message`) and JSON.
  - *Target*: Add an optional Cargo feature (`features = ["miette"]`) that enables rich, syntax-highlighted source snippets with colored squiggly underlines and clickable rule documentation URLs, while keeping the default pre-commit hook binary lightweight and fast.
- **Polished Diagnostic Summaries (`pluralizer` / Native Helper)**:
  - *Target*: Clean grammatical inflection ("1 violation" vs "3 violations") in terminal summary footers, JSON reports, and future JUnit/SARIF export formats.

## 5. Tags, Discovery & Documentation

Design rationale: [ADR 007](docs/dev/decisions/007_rule_taxonomy_and_selection.md) (taxonomy and selection) and [ADR 008](docs/dev/decisions/008_rule_documentation_and_discovery.md) (rule docs and discovery). Contributor guide: [docs/dev/tag_guide.md](docs/dev/tag_guide.md).

- **Cross-file rule contributor guide (`docs/dev/adding_a_rule.md`)**: Add a short `## Cross-file code rules` section covering `ProjectCodeRule`, `ProjectContext`, `ProjectExample`, and multi-file `{ "path" => "code" }` `rule_test!` cases alongside `CodeRule` and `CommandRule`.
- **Typed config warnings**: `Config::warnings` holds formatted strings, and a warning about a selector names its canonical label even when the user wrote a synonym. A typed `ConfigWarning` (selector as written, list it came from) would let the playground and JSON output show warnings too.
- **Taxonomy follow-ups**:
  - *Tree order in facet-label errors*: the "use one of its values" error lists topics alphabetically; tree order, as in `--list-tags`, would match the rest of the output. Sort when the message is changed deliberately.
  - *`is_kebab_case` negative cases*: `cargo mutants -f src/rule_declaration.rs` reports four surviving mutants in `is_kebab_case` (replacing the body with `true`, and each `&&` with `||`), because its only caller in tests (`tests/registry.rs`) asserts that registered names pass. Unit cases for an empty name, a leading or trailing hyphen, and uppercase or `_` characters would kill them.
- **Global & Domain-Scoped Configuration (`$XDG_CONFIG_HOME/omnicoach/config.toml`)**:
  - *Status*: **Completed** ([01_understand.md](docs/dev/global_config/01_understand.md), [02_references.md](docs/dev/global_config/02_references.md), [03_design.md](docs/dev/global_config/03_design.md), [04_execution_log.md](docs/dev/global_config/04_execution_log.md), [05_cleanup_and_audit.md](docs/dev/global_config/05_cleanup_and_audit.md)).
  - *Context*: In large monorepos and external team codebases, checking `.omnicoach.toml` into a team directory is not permitted, yet users still want customized baseline rules, test patterns, and per-file ignores across both CLI (`omnicoach code`) and agent lifecycle hooks (`omnicoach hook`). Furthermore, personal command guardrails (such as `edit-of-described-commit`) must remain active even in repositories whose local config focuses solely on code rules.
  - *Domain Precedence*:
    - **Code domain (`code`, `graph`, hook `FileEdit`, `--explain <code-rule>`)**: `--config <PATH>` $\to$ nearest ancestor `.omnicoach.toml` (stopping at VCS root) $\to$ global config (`$XDG_CONFIG_HOME/omnicoach/config.toml` / `~/.config/omnicoach/config.toml`) $\to$ `Config::default()`.
    - **Command domain (`command`, hook `RunCommand`, `--explain <command-rule>`)**: `--config <PATH>` $\to$ global config $\to$ nearest ancestor `.omnicoach.toml` $\to$ `Config::default()`.
  - *Upward Discovery & Glob Anchoring*: Invocations from subdirectories discover ancestor `.omnicoach.toml` files and anchor `per-file-ignores` relative to the repository root directory (`Config.root_dir`).
  - *Hermetic Isolation*: Test harnesses are hermetically isolated via empty/temporary `XDG_CONFIG_HOME`, keeping tests immune to host global configuration.
- **Examples for suppression audits**:
  - *Current*: Code rules document one executed `Example` per language (`RuleDoc.examples`, run by `rule_test!`) and command rules document one executed `CommandExample` (run by `command_rule_test!`). Suppression audits have no harness that could run an example, so they declare `examples: &[]` (enforced empty in `tests/registry.rs`).
  - *Target*: Give suppression audits executed examples once a harness exists (`Example` can be reused directly).
- **Discovery & Documentation Follow-ups**:
  - JSON output for discovery commands (`--format json` for `--list-rules` / `--explain`), and `tags` on JSON diagnostics. Include per-language message overrides (`summary` / `rationale` / `suggestion`), not just the base text.
  - Path-aware status in `explain` (evaluating `per-file-ignores` for a given file path).
  - Generated in-repo rule catalog guarded by a golden-file drift test.
  - Styled Markdown rendering in the terminal.
  - JSON Schema for `.omnicoach.toml` (editor completion). It must be registry-aware, because `rules` is a free map: per-rule keys and defaults, the threshold bounds each rule uses, language sub-tables, and every rule name and tag as a selector value. Document the `#:schema` directive (Taplo) in the README.
  - Typed overlap / sources field linking rules to equivalent Ruff / Clippy rules.
  - Decide whether plain diagnostics keep printing the full rationale and suggestion on every hit.
  - Investigate subcommands (`rules`, `explain`, a default `check`) instead of the `--list-rules` / `--explain` flags.
- **Later / Out-of-Scope Ideas**:
  - **Abstraction-driven auto-tagging**: importing or using a domain helper (e.g. a logging abstraction) automatically attaches its topic tag to the rule.
  - **Computed `recommended` view**: if curated presets are ever introduced, define `recommended` as a computed view (`exact` ∧ `unopinionated`) rather than a second hand-maintained list.
