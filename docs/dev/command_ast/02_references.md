## 1. External & Internal References

### 1.1 `brush-parser` (`0.4.0`, MIT) AST & Word Architecture

- **Crate**: [`brush-parser 0.4.0`](https://docs.rs/brush-parser/0.4.0/brush_parser/) (`https://github.com/reubeno/brush`).
- **Two-stage parsing model** (matching POSIX.1-2017 §2.1 / §2.6):
  1. **Command & Grammar Parser (`brush_parser::Parser` $\to$ `brush_parser::ast::Program`)**:
     - Parses token streams into `Program` $\to$ `CompleteCommand` (`CompoundList`) $\to$ `CompoundListItem(AndOrList, Option<SeparatorOperator>)` $\to$ `AndOrList { first: Pipeline, additional: Vec<AndOr> }` $\to$ `Pipeline { timed, bang, seq: Vec<Command> }`.
     - `ast::Command` has three variants:
       - `Command::Simple(SimpleCommand { prefix: Option<CommandPrefix>, word_or_name: Option<Word>, suffix: Option<CommandSuffix> })`
       - `Command::Compound(CompoundCommand, Option<RedirectList>)` — covers `Subshell(CompoundList)` `( ... )`, `BraceGroup(CompoundList)` `{ ...; }`, `ForClause`, `CaseClause`, `IfClause`, `WhileClause`, `UntilClause`, `Arithmetic(UnexpandedArithmeticExpr)` `(( ... ))`, `ArithmeticForClause`, `ExtendedTest(ExtendedTestExpr)` `[[ ... ]]`.
       - `Command::Function(FunctionDefinition)` — function body wraps a `FunctionBody(CompoundCommand, Option<RedirectList>)`.
     - Inside `SimpleCommand`:
       - `prefix.0` (`Vec<CommandPrefixOrSuffixItem>`) and `suffix.0` (`Vec<CommandPrefixOrSuffixItem>`) cleanly separate:
         - `CommandPrefixOrSuffixItem::IoRedirect(IoRedirect)` (`File`, `Fd`, `HereDocument`, `HereString`, `OutputAndError`),
         - `CommandPrefixOrSuffixItem::AssignmentWord(Assignment, Word)` (`Name = Value` / `Name += Value` with structured `Assignment`),
         - `CommandPrefixOrSuffixItem::Word(Word)` (ordinary CLI argument words),
         - `CommandPrefixOrSuffixItem::ProcessSubstitution(SubshellDirection, CompoundList)` (`<(...)`, `>(...)`).
  2. **Word Expansion Sub-Parser (`brush_parser::word::parse`)**:
     - Takes `word: &str` and `&ParserOptions` and returns `Result<Vec<WordPieceWithSource>, WordParseError>`.
     - Each `WordPieceWithSource { piece: WordPiece, start_index: usize, end_index: usize }` decomposes quoting and expansion:
       - `WordPiece::Text(String)`, `SingleQuotedText(String)`, `AnsiCQuotedText(String)`, `EscapeSequence(String)`
       - `WordPiece::DoubleQuotedSequence(Vec<WordPieceWithSource>)`, `GettextDoubleQuotedSequence(Vec<WordPieceWithSource>)`
       - `WordPiece::CommandSubstitution(String)` (`$(...)`) and `BackquotedCommandSubstitution(String)` (`` `...` ``)
       - `WordPiece::ParameterExpansion(ParameterExpr)` (`$VAR`, `${VAR:-default}`, etc.)
       - `WordPiece::ArithmeticExpression(UnexpandedArithmeticExpr)` (`$((...))`)
       - `WordPiece::TildeExpansion(TildeExpr)` (`~`)
- **Source Locations (`brush_parser::SourceSpan`) & Three Critical Source-Level Findings**:
  - Every `ast` node implements `ast::SourceLocation::location(&self) -> Option<SourceSpan>`, where `SourceSpan { start: SourcePosition, end: SourcePosition }` and `SourcePosition { index: usize, line: usize, column: usize }`.
  - **Empirical Finding 1 (`SourcePosition.index` is a Unicode `char` index, not a UTF-8 byte offset)**:
    - In `brush-parser-0.4.0/src/tokenizer.rs:571` (`next_char`), `self.cross_state.cursor.index += 1` increments by `1` per `char` (`utf8_chars::Chars`), whereas `omnicoach::diagnostic::SourceSpan` and `brush_parser::word::WordPieceWithSource { start_index, end_index }` (generated by `peg::parser!` `position!()` on `&str` in `word.rs`) use **0-based UTF-8 byte offsets**.
    - Therefore, `command_lint::command` must convert `brush_parser::SourcePosition.index` to UTF-8 byte offsets via a `CharToByteMap` ($O(1)$ identity when `source.is_ascii()`, or a `char_indices()` lookup table when non-ASCII characters are present).
  - **Empirical Finding 2 (`ast::IoRedirect::location()` returns `None` in `brush-parser 0.4.0`)**:
    - In `brush-parser-0.4.0/src/ast.rs:1503`, `impl SourceLocation for IoRedirect` has `// TODO(source-location): complete` and returns `None`. Because `CommandPrefix::location()` and `CommandSuffix::location()` (`ast.rs:941, 969`) return `None` whenever the first or last item's `location()` is `None`, any `SimpleCommand` ending in a redirection (`jj edit @- > out.txt`) has `suffix.location() == None`, causing `SimpleCommand::location()` to truncate the command's span to `"jj"`.
    - However, every target `Word` inside `IoRedirect` (`IoFileRedirectTarget::Filename(word)`, `Duplicate(word)`, `OutputAndError(word, _)`, `HereString(_, word)`, `IoHereDocument { here_end, doc, .. }`) and `SubshellCommand` (`ProcessSubstitution(_, subshell)`) **does** store its exact `SourceSpan` (`word.loc` / `subshell.loc`), and `brush_parser::tokenize_str_with_options` + `brush_parser::parse_tokens` expose the full `[Token]` stream (including redirection operator tokens `>`, `>>`, `2>&1`). Computing spans in `command_lint::command` from the token stream and child `Word.loc`s recovers 100% accurate spans for both `CommandRedirect` and `InterceptedCommand`.
  - **Empirical Finding 3 (`word::parse` vs `unquote_str`)**:
    - `brush_parser::unquote_str` (`tokenizer.rs:1323`) is a naive character loop that strips `\` and `'` even inside single-quoted literals (`unquote_str(r"'hel\'lo'") == r"hel'lo"`).
    - Instead, `brush_parser::word::parse(raw_word, &options)` parses `WordPiece`s according to POSIX/Bash quoting rules (`SingleQuotedText`, `DoubleQuotedSequence`, `AnsiCQuotedText`, `EscapeSequence`, `Text`, `CommandSubstitution`, `BackquotedCommandSubstitution`, `ParameterExpansion`, `ArithmeticExpression`, `TildeExpansion`), providing both exact unquoting and recursive extraction of `$(...)` and `` `...` `` command substitutions with byte-offset mapping back to the outer command string.

### 1.2 SOTA Shell Linters (`ShellCheck` & `mvdan/sh`)

- **ShellCheck** (`src/ShellCheck/Analytics.hs` & `Checker.hs`):
  - Parses the script once into a `ParseResult` containing the root AST, and exposes **both** `treeChecks` (whole-script checks that need cross-command or structural flow, such as tracking `cd dir` across sequential commands) and `commandChecks` (checks parameterized on a single `Token` representing a simple command, such as `checkUuoc` for `cat`, `checkFind`, `checkGrep`).
  - Pre-extracts a flat list of all commands in the AST (including commands nested inside `$(...)`, subshells `(...)`, loops, and branches) so per-command checks do not each write their own tree traversal.
- **Internal Reference: `code_lint` ([`src/code_lint/ast.rs`](../../../src/code_lint/ast.rs) & [`src/code_lint/contract.rs`](../../../src/code_lint/contract.rs))**:
  - `ParsedFile::new(source, lang)` parses the input once, encapsulates the third-party parser crate (`ruff_python_parser` / `ra_ap_syntax`), exposes `has_syntax_error()`, and provides high-level structural extractors (`call_candidates`, `bindings`, etc.).
  - `CodeRule::check` takes `(rule, path, &ParsedFile, options)` and uses `rule.diagnostic_at_node(path, &node, params)` so rule files never construct `SourceLocation` manually or touch raw parser types.

## 2. Deep Dive on `Q2`: `ParsedCommand` Container vs. Bare `&InterceptedCommand`

### 2.1 What Happens When Rules Only See One `&InterceptedCommand` at a Time?

If `CommandRule::check` has signature `fn(&Self, &InterceptedCommand, &dyn JjClient) -> Vec<Diagnostic>`, each rule invocation sees one isolated command without the surrounding `ParsedCommand`. Let's test this against concrete roadmap rules:

1. **Sequential Context Across Commands (`cd` and `jj` state transitions)**:
   - **Example 1 (`executable-existence` rule)**:

     ```bash
     cd tools && ./lint.sh
     ```

     When checking `./lint.sh` relative to `Cwd`, the rule needs to know that an earlier command in the same `&&` chain ran `cd tools`. If the rule only sees `&InterceptedCommand` for `./lint.sh`, it checks `Cwd/./lint.sh` instead of `Cwd/tools/./lint.sh` (a false positive).
   - **Example 2 (`jj` rules on chained commands)**:

     ```bash
     jj new d123 && jj squash -m "fold fix"
     ```

     Or:

     ```bash
     jj describe -m "feat: done" && jj edit @
     ```

     Earlier commands in the same `CommandLine` mutate the working copy state that subsequent commands in the chain operate on.
2. **Whole-Command-Line Shape Rules (`prefix-approvable-command-shape`)**:
   - When flagging multi-command chains (`cmd1 && cmd2 && cmd3`) or pipelines (`cmd1 | cmd2 | cmd3`), a whole-line rule wants to inspect the command line once (or flag each prohibited operator/construct once), rather than running inside a per-command loop and having to guess whether it is on the first, second, or third command.
3. **Eliminating Cloned Strings and Diagnostic Plumbing**:
   - Today, `InterceptedCommand` owns `pub(super) raw_string: String`. For a 4-command pipeline `a | b | c | d`, `raw_string` is allocated and copied 4 times.
   - With `ParsedCommand<'a>` holding `source: &'a str` and `commands: Vec<InterceptedCommand>`:
     - `raw_string` is borrowed once on `ParsedCommand<'a>`.
     - `CommandRule` provides `rule.diagnostic_at(parsed, span, &[("revision", &revision)])`, hiding `SourceLocation::virtual_span(VCS_CONTEXT_NAME, ...)` inside `CommandLintContract` (just as `CodeRule::diagnostic_at_node` hides `node.to_source_location(path)` inside `CodeLintContract`).
4. **Keeping Per-Command Rules Ergonomic**:
   - Just as `CodeRule` has helper methods (`check_banned_calls`, `check_banned_suffixes`) in `src/code_lint/contract.rs`, `ParsedCommand` exposes `parsed.commands() -> &[InterceptedCommand]`.
   - For a per-command rule like `edit-of-described-commit`, checking all commands in `parsed.commands()` is a single `for cmd in parsed.commands()` loop (or `parsed.commands().iter().filter_map(...)`), and in `test_utils` `run_command_rule(rule, command_line, jj_client)` runs the rule over the entire `ParsedCommand`—fixing the `.remove(0)` bug in `test_utils.rs`!

### 2.2 What Each `InterceptedCommand` Inside `ParsedCommand` Contains

```rust
pub struct ParsedCommand<'a> {
    source: &'a str,
    has_syntax_error: bool,
    commands: Vec<InterceptedCommand>,
}

pub struct InterceptedCommand {
    /// Executable word (e.g. `jj` or `/usr/bin/jj`), with unquoted value, raw text, and byte span.
    pub program: CommandWord,
    /// Arguments passed to the command (excluding redirections and leading env assignments).
    pub arguments: Vec<CommandWord>,
    /// Leading `NAME=VALUE` environment variable assignments on this command.
    pub env_assignments: Vec<EnvAssignment>,
    /// Input/output redirections (`> file`, `2>&1`, `<<EOF`, etc.) attached to this command.
    pub redirects: Vec<CommandRedirect>,
    /// Structural context (connectors `&&`/`||`/`|`/`&`/`;`, subshell `(...)`, command substitution `$(...)`).
    pub context: CommandContext,
    /// Full byte span of this simple command in `ParsedCommand::source`.
    pub span: SourceSpan,
}
```

### 3.2 Why Command Rules Need Two Things for Examples

1. **Fence language in `Example`**:
   - Code rules analyze `Language::Python` (`"python"`) and `Language::Rust` (`"rust"`). Note that `Language` is also used everywhere for `.omnicoach.toml` per-language option tables (`[rules.<name>.python]`, `[rules.<name>.rust]`) and `Language::from_path`, so we must **not** add `Shell` to `enum Language` (which would falsely allow `[rules.<name>.shell]` in config and break `Language::VARIANTS` in code rules).
   - Instead, in `documentation.rs`, `Example` can either:
     - Have `language: Option<Language>` (with `Example::shell(flagged, flagged_span, fixed)` or `language: None` rendering as ```` ```sh ```` in `rule_catalog.rs`), **or**
     - Keep `Example` for code rules (`language: Language`) and add `CommandExample { flagged, flagged_span, fixed }` (or `Example` with an enum `ExampleLang { Code(Language), Shell }`).
2. **Repository state (`JjClient`) when executing the example**:
   - A code rule example is self-contained source text (`run_code_rule(rule, example.flagged, "example.py")`).
   - A command rule like `edit-of-described-commit` queries `jj_client.get_commit_info(revision)`. For `flagged: "jj edit kpqxywon"` to trigger `edit-of-described-commit`, the test runner's `FakeJjClient` must know that `"kpqxywon"` is a described commit!
   - Because `command_rule_test!` already declares the rule's `FakeJjClient` table (`jj: [ "kpqxywon" => described("..."), ... ]`), `command_rule_test!` can pass that exact `FakeJjClient` to `assert_command_documented_examples(&RULE, &jj_client)`!
   - That way:
     - `RuleDoc` stays pure static data (no `FakeJjClient` inside `RuleDoc`),
     - `omnicoach --explain edit-of-described-commit` renders the `## Example` section with ```` ```sh ```` blocks,
     - `command_rule_test!` verifies that `example.flagged` triggers the rule on `example.flagged_span` (including when repeated as `"{flagged} && {flagged}"`) and `example.fixed` produces 0 diagnostics!
     - `tests/registry.rs` enforces that every command rule documents 1 shell example (`test_command_rules_document_one_shell_example`).
